# TC 작성 가이드

TC(테스트 케이스)는 `qa-workspace` 저장소의 마크다운 파일이다. 앱의 TC 메뉴에서 쓰고 고치면, 저장할 때 규칙 검사(린트)를 하고 작업 브랜치에 커밋한다. **PR 작성**으로 PR 을 만들고, 승인자가 머지하면 승인된 것이다.

## 파일과 위치

- `testcases/<앱>/TC-0101.md` — 한 파일에 TC 하나. id 는 `TC-` + 4자리 이상 숫자. 새 TC 는 TC 메뉴의 **새 TC**가 다음 번호와 틀을 만든다.
- 플로우는 따로 `flows/<앱>/<타깃>/TC-0101.yaml`. 사람이 쓰거나 "플로우 만들기"(에이전트)가 만든다.

## 형식

```markdown
---
id: TC-0101
title: 이메일로 회원가입하면 홈 화면이 열린다
app: demo
targets: [ios]
priority: high
tags: [smoke, auth]
account: signup
status: active
---
## 전제조건
- 로컬 dev 서버가 실행 중이다
- 로그인하지 않은 상태로 앱을 처음 연다

## 스텝
1. '이메일로 계속하기'를 탭한다
   - 기대: 회원가입 화면이 열리고 이메일·비밀번호·닉네임 입력란과 '가입하기' 버튼이 보인다
2. 새 이메일, 테스트 비밀번호, 닉네임을 입력하고 '가입하기'를 탭한다
   - 기대: 홈 화면이 열리고 '새 메모 작성'과 '설정 열기'가 보인다

## 완료 기준
- 가입 후 홈 화면에서 '새 메모 작성' 표시
```

| 머리 항목 | 필수 | 값 |
|---|---|---|
| `id` | 예 | 파일 이름과 같다 |
| `title` | 예 | 120자 이내. 결과가 드러나게("…하면 …가 열린다") |
| `app` | 예 | `workspace.yaml`의 앱 id |
| `targets` | 예 | `ios`, `android` 등. `app.yaml`에 있는 타깃 |
| `status` | 예 | `draft`(작성 중), `active`, `deprecated` |
| `priority`, `tags` | 아니오 | `high`·`medium`·`low`, 자유 태그 |
| `account` | 계정이 필요하면 | `apps/<앱>/accounts.yaml`의 **계정 역할 이름**(예: `signup`, `student`). 값이 아니다 |

## 잘 쓰는 법

- 스텝 하나에 동작 하나. 누를 대상이나 볼 문구는 화면 글자 그대로 작은따옴표로 쓴다: `'가입하기'를 탭한다`.
- 모든 스텝에 `- 기대:`를 쓴다. 기대는 화면에서 **보이는 것**으로 쓴다(문구, 버튼, 화면 이름). "정상 동작한다"처럼 확인할 수 없는 말은 피한다.
- 앱 실행·로그아웃 상태 만들기는 스텝이 아니라 전제조건이다. 앱 실행은 공통 서브플로우가 한다.
- 비밀번호·아이디 같은 값은 쓰지 않는다. `account`로 역할만 적고, 값은 각자 앱 설정에 저장한다.
- 실제 결제, 외부 전송(공유·메일·전화), 탈퇴 같은 되돌릴 수 없는 동작은 TC 로 자동화하지 않는다.

## 린트 (저장할 때 검사)

| 규칙 | 수준 | 고치는 법 |
|---|---|---|
| 머리 항목 형식(id, title, app, targets, status) | 오류 | 위 표대로 |
| 스텝 1개 이상, 완료 기준 1개 이상 | 오류 | `## 스텝`, `## 완료 기준` 아래 목록 |
| 스텝마다 동작과 "기대" | 오류 | 스텝 아래 `- 기대: …` |
| `account`가 accounts.yaml 의 역할 | 오류 | 역할 이름 확인, 없으면 아래 "앱 설정"에서 추가 |
| "앱을 실행한다" 류 스텝 | 경고 | 전제조건으로 옮긴다 |
| "선택한다·확인한다"만 있는 모호한 스텝 | 경고 | 대상·문구를 따옴표로 |
| `app.yaml`에 없는 타깃 | 경고 | 타깃 이름 확인 |

오류가 있으면 저장되지 않는다. 경고는 저장되지만 고치는 것이 좋다.

## 저장과 검토

1. TC 메뉴에서 쓰고 **저장** → 그 TC 의 작업 브랜치 `qa/<내 아이디>/<TC>-<요약>` 에 커밋한다.
   - TC 하나에 작업 브랜치 하나, PR 하나다. 다른 TC 의 브랜치에 있어도 그 TC 의 브랜치로 옮겨(없으면 main 에서 새로 만들어) 커밋한다.
   - 커밋하지 않은 변경이 있거나 실행·플로우 만들기가 진행 중이면 브랜치를 옮기지 않고 알린다. 끝난 뒤 다시 저장한다.
2. TC 화면의 **작업 브랜치** 표에서 내 브랜치를 본다.
   - TC 목록은 지금 브랜치의 내용이다. 아직 머지되지 않은 다른 TC 의 변경은 그 브랜치의 **체크아웃**을 누르면 나온다.
   - **PR 작성** → 아래에 PR 제목·본문 양식이 열린다. **PR 올리기**를 누르면 그 브랜치를 올리고 PR 을 만든다. 같은 브랜치의 열린 PR 이 있으면 그 PR 에 올린다. 승인자(CODEOWNERS)가 리뷰하고 머지한다. 앱은 자동으로 머지하지 않는다.
3. 변경 내역에서 그 TC 파일의 커밋을 본다.

## 앱 설정 (app.yaml · accounts.yaml)

테스트할 앱마다 이름·언어·**타깃별 앱 ID**(iOS 번들 ID, Android 패키지)와, TC 의 `account` 로 고르는 **계정 역할**(역할 이름 → 키 이름, 값이 아니다)이 있다. TC 편집 화면의 타깃 체크박스와 계정 역할 목록은 여기서 정한 것만 나온다.

1. 사이드바 **워크스페이스** → **앱 설정**에서 앱을 고른다. 새 앱이면 **＋ 새 앱**을 고르고 앱 ID(영문 소문자·숫자·하이픈, 나중에 바꿀 수 없음)를 쓴다.
2. 이름·언어(예: `ko_KR`, 비우면 워크스페이스 기본값)를 쓰고, 쓰는 타깃을 체크해 앱 ID 를 넣는다. iOS 는 **iOS 빌드 기본값**(스킴·구성)도 적을 수 있다. 빌드 화면의 프로젝트 빌드가 이 값을 먼저 고른다.
3. 계정이 필요하면 **역할 추가**로 역할 이름·설명·키 이름(쉼표로 구분)을 쓴다.
   - 역할 이름: 영문 소문자로 시작, 소문자·숫자·하이픈 (예: `member`)
   - 키 이름: 영문 대문자·숫자·밑줄 (예: `APP_MEMBER_EMAIL`)
4. **변경 요약**을 쓰고 **저장(커밋)** → 그 앱의 앱 설정 작업 브랜치 `qa/<내 아이디>/app/<앱>/<요약>` 에 app.yaml·accounts.yaml(새 앱이면 workspace.yaml 앱 목록까지)만 커밋한다. TC 변경과 섞이지 않는다.
5. **PR 작성** → 승인자가 머지하면 모두의 워크스페이스에 들어간다. TC 화면의 작업 브랜치 표에서도 "앱 설정 · <앱>" 줄로 보인다.
6. 계정 키의 **값**은 설정 → 테스트 계정 값에서 각자 넣는다.

지우면 안 되는 것은 저장할 때 막는다: TC·플로우가 쓰는 타깃, TC 가 쓰는 역할, 플로우가 `${KEY}` 로 쓰는 키. 형식이 틀리거나 바뀐 것이 없어도 저장하지 않는다.

## 플로우 만들기 (에이전트, 선택)

플로우 만들기 메뉴에서 TC·타깃·실행 중인 기기(·빌드)를 고르고 시작하면, 에이전트가 기기에서 TC 를 따라가며 Maestro 플로우를 만든다.

- 시작하면 앱이 그 TC 의 작업 브랜치(없으면 main)로 옮긴다. 진행 중에는 다른 화면에서 브랜치를 바꾸지 않는다.
- 작업은 시작할 때 읽은 TC 로 만든다. 진행 중에 그 TC 를 저장하려 하면 경고하고, "반영되지 않는 것을 알고 저장" 을 체크해야 저장한다.
- 다른 메뉴에 갔다 와도 플로우 만들기 화면에 진행 중인 작업이 다시 보인다.
- 앱이 플로우 규약을 검사하고 같은 기기에서 **두 번** 재생한다. 둘 다 통과해야 그 TC 의 작업 브랜치에 플로우와 meta 를 커밋한다. 안 되면 문제를 알려 한 번 다시 시도한다.
- 에이전트에게는 계정 값의 **키 이름**만 보인다. 기기 캡처는 에이전트가 본다(비밀번호 칸은 OS 가 가린다).
- 비용: 작업당 상한 $5, 월 상한은 설정의 값. 설정의 LLM 사용량에서 이번 달 비용을 본다.
- 결과 화면에 식별자 누락(텍스트로 대신 찾은 요소)과 기획자 질문이 나온다. 질문은 TC 를 고쳐 답한다. 식별자 누락은 앱 팀에 accessibility id 추가를 요청할 목록이다.
